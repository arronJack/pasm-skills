# 服务器需求评估（SERVER-NEEDS）

> 结论先行：**当前阶段不需要任何自有服务器。**
> 本文把"哪些确实需要服务器、哪些只是看起来需要"逐条拆开记录，
> 需要服务器的部分**一律标记为 SKIP 并跳过**，不阻塞任何现在的开发。

评估时间：2026-09-12 · 对应版本：PASM Skills v0.1.0

## 二、三条"零服务器"的长期验证路径（推荐按顺序升级）

### 路径 A：本地手动（今天就能用）

```bash
python -m pasm_skills run --all --out reports/$(date +%F).json
```

优点：零配置、离线可跑。
缺点：靠人记得。

### 路径 B：本地定时（推荐现在就用）

- **Windows 任务计划**：每天固定时间跑一次 `run --all --out reports\YYYY-MM-DD.json`；
- **本机助手定时任务**：在会话里直接说"每天早上 9 点对 PASM 跑一次全量验证并归档"，
  即可建立一条定时任务（由本机执行，不需要服务器）。

优点：自动化、有归档、不需要任何外部服务。
缺点：电脑关机时不跑（对"验证"来说完全可接受——下次开机补跑即可）。

### 路径 C：GitHub Actions（公开仓免费，等于借用别人的服务器）

公开仓可无限使用 GitHub Actions。把智能体推上去，加一个 workflow 定时跑，
结果以 artifact 形式归档，FAIL 时自动开 issue。

**关键点：这仍然不需要自有服务器** —— 用的是 GitHub 的托管机器。

> 现状：本仓已具备可直接接入 CI 的条件（退出码 `0`/`1` 语义清晰、`--json` 可归档）。
> workflow 文件留待接入时再写，避免现在引入无用配置。

## 三、真正需要服务器时，需要什么（**记录并跳过**）

以下内容**现在不采购、不部署、不预留**，仅登记需求，等真的要做常驻服务时再启用。

### 3.1 触发条件

满足**任一**条件时才需要考虑：

- 需要**在自己电脑关机时**仍然持续运行对外服务；
- 需要给第三方提供**稳定的公网地址**（Webhook 回调、API 端点、Web 面板）；
- 需要多台机器协同的**集中调度**（智能体数量、并发度超出单机）。

### 3.2 最小可行配置（届时参考）

| 项 | 建议 | 说明 |
|---|---|---|
| 形态 | 云主机（国内：阿里云/腾讯云轻量；海外：任意 VPS） | 按量或按月，**按需开、用完关** |
| 规格 | 2 核 4G 起 | 只是跑验证/调度，不需要 GPU |
| GPU | **不需要** | 验证智能体零依赖；训练走按小时租用 |
| 系统 | Ubuntu LTS | 与 PASM 的 Linux 部署路径一致 |
| 对外端口 | 一个（80/443，走反向代理） | 便于合规与证书管理 |
| 存储 | 40G 起 | 归档验证报告 |
| 备案 | 国内主机对外提供 Web 服务需备案 | **这是最容易被低估的成本** |

### 3.3 需要一并准备的东西

- 域名（若对外提供 Web 服务）与 HTTPS 证书；
- 密钥管理（不要把 token 硬编码，走环境变量或密钥服务）；
- 监控与告警（服务挂了要知道）——这本身又增加运维负担。

### 3.4 为什么现在不做

1. **当前没有任何功能依赖常驻服务**：三步改造、智能体验证全是本地可完成；
2. **引入服务器的隐性成本高**：备案、证书、监控、运维、安全补丁，都会摊薄真正做产品的精力；
3. **替代方案已经够用**：路径 B/C 已能覆盖"定时 + 自动化 + 归档 + 告警"，
   且**在需要时可以不改一行代码就切换到服务器**（智能体是 CLI，无状态）。

> 一句话：**服务器是"要做对外服务"时才付的账，不是"要做验证"的前提。**
